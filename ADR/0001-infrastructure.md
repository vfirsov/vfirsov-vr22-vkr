# ADR-0001: Выбор инфраструктуры для веб-системы чайного магазина (Local / Demo / Prod)

| Поле | Значение |
| --- | --- |
| Статус | DRAFT |
| Автор | Фирсов В. Д. |

## 1. Краткое предложение

Предлагается до начала разработки зафиксировать инфраструктуру для Local-контура разработки, Demo-стенда и Prod-контура: для каждого контура — вариант размещения, схему развёртывания и стоимость. Сравнение вариантов и выбор — в разделах 4–5.

## 2. Цели и границы решения

**Цели — три контура:**

1. **Local (на рабочей машинке)** — единое окружение разработки на каждом из двух рабочих мест автора.
2. **Demo (демонстрационный)** — инфраструктура временного размещения: поднимается, чтобы показать промежуточный результат заказчику. Одноразовая — пересоздаётся из репозитория; требований к HA и failover не предъявляется.
3. **Prod (рабочий)** — целевая инфраструктура системы. Проектируется под реальную эксплуатацию: HA и failover — обязательные требования к целевому решению.

## 3. Требования и ограничения

**Соответствие 12 Factor App.** Сервисы системы должны проектироваться и разрабатываться в соответствии с методологией [12 Factor App](https://12factor.net/ru/). Переход между контурами (Local → Demo → Prod) должен выполняться изменением конфигурации, без модификации кода и отдельных сборок под каждый контур.

### Local (на рабочей машинке)

**Воспроизводимость среды разработки.** Окружение, схема БД и исходные данные должны автоматически разворачиваться на домашнем и рабочем компьютерах из версионируемых файлов проекта, без ручной настройки.

**Независимая разработка компонентов.** Среда должна обеспечивать изменение и отладку backend и frontend независимо друг от друга.

**Простой запуск зависимостей.** Неизменяемые компоненты и БД должны запускаться изолированно, без настройки их среды разработки на компьютере.

### Demo (демонстрационный)

**Доступность и восстановление.** Demo-стенд должен быть доступен через интернет для демонстрации функциональности сервиса. При сбое отдельных компонентов должен обеспечиваться их автоматический перезапуск. Допускается временная недоступность при сбоях, обновлении и обслуживании; резервирование компонентов и гарантированное время восстановления не требуются.

### Prod (рабочий)

**Доступность и отказоустойчивость.** Prod-контур должен обеспечивать работу сервиса в режиме 24/7 с заданным SLO доступности. Отказ одного экземпляра приложения и плановое развёртывание новой версии не должны прерывать обслуживание.

**Надёжность обработки заказов.** Подтверждение приёма заказа должно выполняться только после его устойчивого сохранения. Обработка должна поддерживать повторные попытки и идемпотентность операций, исключая потерю принятых заказов и повторное выполнение списаний.

**Резервное копирование и восстановление.** Для данных должны быть определены RPO и RTO — допустимая потеря данных по времени и срок восстановления. Резервное копирование должно выполняться автоматически, а восстановление — регулярно проверяться.

**Безопасность и изоляция.** Prod-контур должен быть изолирован от сред разработки и демонстрации. Необходимо обеспечить шифрование соединений, минимально необходимые права доступа, защищённое хранение секретов и аудит административных действий.

**Наблюдаемость и производительность.** Должны собираться метрики, логи и статусы обработки заказов; нарушения доступности и ошибки — вызывать оповещения ответственных. Производительность должна соответствовать заданным ограничениям на время ответа и обработку заказов при расчётной пиковой нагрузке.

## 4. Рассмотренные варианты

### Demo-стенд

#### VPS с Docker (предлагаемое решение)

Арендуется виртуальная машина у хостинг-провайдера (Timeweb, Selectel, Hetzner и аналоги); достаточно конфигурации порядка 2 vCPU / 4 ГБ RAM. На машину устанавливается Docker, backend, frontend и PostgreSQL запускаются через Docker Compose — те же образы контейнеров, что и в Local-контуре (раздел 3). Развёртывание и обновление — из репозитория по SSH (`git pull` + `docker compose up -d`), данные восстанавливаются seed-скриптами. Стенд пересоздаётся с нуля скриптом за 10–15 минут; при почасовой тарификации оплачивается только время демонстраций.

#### Альтернатива: локальная машина с публичным IP

Хостом выступает домашний или рабочий компьютер: либо белый IP-адрес от провайдера с пробросом портов на роутере, либо — при сером или динамическом IP — туннель (Cloudflare Tunnel, ngrok) или VPN (Tailscale) с публичной точкой входа. Вычислительных ресурсов у такой машины больше, чем у дешёвого VPS.

#### Альтернатива: managed Kubernetes

Управляемый кластер Kubernetes в облаке (Yandex Cloud, VK Cloud, Selectel) с управляемой СУБД (DBaaS): декларативные манифесты, самовосстановление подов, горизонтальное масштабирование.

#### Альтернатива: k3s на VPS

Легковесная сборка Kubernetes для одного узла, разворачивается на той же виртуальной машине, что и предлагаемый вариант; оверхед оркестратора — порядка 512 МБ RAM. Даёт полноценный API Kubernetes (`kubectl`, манифесты, пробы) — например, на защите можно показать восстановление сервиса после аварийного завершения контейнера.

#### Сводное сравнение

| Критерий | VPS с Docker | Локальная машина с публичным IP | managed Kubernetes | k3s на VPS |
| --- | --- | --- | --- | --- |
| Стоимость | 200–500 ₽/мес или 1–3 ₽/час почасово | бесплатно | тысячи ₽/мес, тарификация круглосуточно | те же 200–500 ₽/мес за VPS |
| Публичная ссылка | постоянная | нестабильна — серый или динамический IP | постоянная | постоянная |
| Доступность | не зависит от домашнего интернета | пока машина включена и канал работает | не зависит от домашнего интернета | не зависит от домашнего интернета |
| Отказ хоста | простой стенда — для Demo допустимо (раздел 2) | простой стенда плюс бытовые факторы | перекрывается HA — для Demo не требуется (раздел 2) | простой стенда — узел по-прежнему один |
| Самовосстановление сервисов | рестарт-политики Docker Compose | — | пробы, самовосстановление подов | пробы, самовосстановление, `kubectl scale` |
| Сложность и обслуживание | минимальные: Linux и Docker, ОС обслуживаем сами | настройка туннеля или проброса портов | высокая: кластер, манифесты, DBaaS | выше Compose: ingress, манифесты, тома; ОС и кластер — сами |
| Путь к Prod | — | — | совпадает с кандидатом на Prod-контур | опыт Kubernetes API без стоимости managed-кластера |
