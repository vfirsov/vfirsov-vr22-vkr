# Чайный магазин — информационная веб-система

Веб-система для чайного магазина: покупатель подбирает чай по типу, региону, обработке и вкусу и оформляет заказ, администратор ведёт ассортимент, остатки и заказы.

Текущий статус проекта на **16.11.2026** — в [`status.md`](status.md): что реализовано, какие функции отсутствуют и какие заявленные результаты не подтверждены для текущей версии.

> ВКР «Разработка информационной веб-системы для управления продажами и учёта ассортимента в чайном магазине», РАНХиГС, 09.03.03 «Прикладная информатика». Автор — Фирсов В. Д., руководитель — доц. Пономарёва Л. А. Текст работы — в [`docs/`](docs/).

## Назначение и результат

### Проблема

Работа магазина без единой информационной системы и низкая степень автоматизации деятельности ограничивают эффективность процесса продаж и возможности увеличения их объёма без пропорционального роста нагрузки на сотрудников.

- **Приём и сопровождение заказов.** Заказы и обращения поступают по разным каналам. История общения с покупателем не имеет единого источника правды и хранится в разрозненных каналах коммуникации.
- **Учёт остатков.** Ручное обновление данных приводит к расхождениям между фактическим наличием и доступным для заказа количеством. Возникает риск продажи отсутствующего товара.
- **Возвраты и обращения по качеству и комплектации заказов.** Сведения об обращениях покупателей, заказах и поставках хранятся раздельно. Это затрудняет выяснение обстоятельств инцидента и организацию возврата или замены товара. Если проблема связана с поставкой, сотрудникам также сложно определить партию, поставщика и остатки товаров этой партии.
- **Контроль наличия и планирование закупок.** Без актуальных сведений об остатках и продажах сложно вовремя определить потребность в пополнении ассортимента. Это создаёт риск дефицита востребованных позиций и накопления невостребованного товара.

### Пользователи и основной сценарий

- **Покупатель:** просматривает каталог, применяет фильтры, добавляет товары в корзину, оформляет заказ и отслеживает статус в личном кабинете.
- **Администратор:** товары и категории, остатки, статусы заказов, отчёты.

### Что считать успешным результатом

Целевой результат — работающая веб-система, в которой покупатель оформляет заказ, а администратор обрабатывает его и ведёт ассортимент и остатки. Результат считается достигнутым, когда выполнены следующие условия:

1. **Покупка без помощи сотрудника.** Покупатель находит чай с помощью каталога и фильтров, добавляет товары в корзину, оформляет заказ и видит его состав, сумму и статус в личном кабинете.
2. **Обработка заказа.** Администратор видит оформленный заказ и меняет его статус; покупатель видит обновление. Заказ сохраняется в БД и остаётся доступным после перезапуска приложения.
3. **Ассортимент и остатки.** Администратор изменяет товары, категории и остатки. Изменения отражаются в каталоге; оформление заказа учитывает доступное количество и не допускает продажи сверх остатка, в том числе при одновременных заказах.
4. **Разграничение доступа.** Покупатель видит только свои заказы; изменение ассортимента, остатков и статусов доступно только администратору. Ограничения проверяются на стороне API.
5. **Подтверждённая работоспособность.** Сценарии выше проверены на текущей версии системы, результаты зафиксированы. При нагрузке 100 запросов/с максимальное время ответа API не превышает 2 с, доля ошибок для корректных запросов — 0 %. В отчёте указаны версия кода, окружение, набор данных, сценарии, длительность нагрузки, максимальное время ответа и доля ошибок; тайм-ауты учитываются как ошибки.

Это критерии приёмки полной системы. Степень их выполнения и сведения о проверках приведены в [`status.md`](status.md).

## Архитектура

Целевая архитектура системы: frontend на Nuxt 4 с серверным рендерингом, API на Flask и PostgreSQL. HTTPS и маршрутизацию домена на контейнер обеспечивает Amvera, отдельный Nginx не используется. В текущем репозитории реализованы frontend с каталогом, API чтения каталога и схема БД для категорий и товаров.

```mermaid
flowchart LR
  B[Браузер] -- HTTPS --> FE[Nuxt 4 SSR<br>витрина и админ-панель]
  FE -- "REST / JSON при SSR" --> API[Flask + Granian]
  B -- "REST / JSON при клиентской навигации, CORS" --> API
  API -- SQLAlchemy --> DB[(PostgreSQL)]
  API -.-> EXT[YooKassa, СДЭК]
```

- **Frontend** — одно приложение Nuxt 4 (Vue 3, TypeScript) с серверным рендерингом на Nitro (`node-server`). При открытии страницы запрос к API выполняет сервер Nuxt (SSR); при дальнейшей навигации браузер обращается к API сам, поэтому API отдаёт CORS-заголовки на домен frontend. Реализованы стартовая страница, каталог и страница 404; корзина, вход и личный кабинет не реализованы, админ-панель планируется как маршруты этого же приложения с доступом по роли.
- **API** — Flask + Granian, доступ к БД через SQLAlchemy, схема управляется миграциями Alembic. Целевой API: каталог с фильтрами, корзина, заказы, остатки, вход по JWT и проверка роли на стороне API. Реализовано только чтение каталога.
- **БД** — PostgreSQL. Реализованы таблицы `categories` и `products`; таблицы пользователей, заказов и остатков не реализованы.
- Frontend, API и БД — три отдельных проекта Amvera; API обращается к БД по внутреннему адресу, у БД нет внешнего домена.
- Пунктир — внешние интеграции из материалов ВКР: оплата YooKassa и доставка СДЭК. В текущем репозитории они не реализованы.

### Настройки localhost

- **Порты:** frontend `3000`, API `8080`, PostgreSQL `5432`. Порт `3000` входит в CORS allowlist API (см. раздел «Конфигурация»): при другом порте или адресе frontend `/catalog` отрисуется на сервере, но браузер заблокирует клиентские запросы к API.
- **`DATABASE_URL`** — нужна в окружении терминала, где выполняются `manage_catalog.py` и Granian; без неё миграции не запускаются, а `/api/catalog` отвечает `503`. Формат — в разделе «Конфигурация».
- **`NUXT_PUBLIC_API_BASE_URL`** — по умолчанию `http://127.0.0.1:8080`, для локального запуска менять не нужно. Полное описание — в разделе «Конфигурация».
- **Локальный PostgreSQL в Docker** описан в `docker-compose.yml`: образ `postgres:17`, контейнер `vkr-postgres`, сеть `vkr`, порт `127.0.0.1:5432`, именованный том для данных и healthcheck. Логин, пароль и имя базы Compose берёт из корневого `.env`; шаблон с парой `vkr`/`vkr` — `.env.example`.

Перед первым запуском из корня проекта создайте `.env` из шаблона, если файла ещё нет. В PowerShell выполните `if (!(Test-Path .env)) { Copy-Item .env.example .env }`, в Linux или macOS — `test -f .env || cp .env.example .env`. Затем в том же каталоге:

```sh
docker compose up -d postgres
docker compose ps postgres
```

Дождитесь статуса `healthy`. Для запуска API на хосте загрузите `DATABASE_URL` в тот терминал, где будете запускать миграции и сервер (команды для каждой ОС есть в [Quick Start](#запуск-в-локальном-окружении)). Если меняете логин, пароль или имя базы, правьте их в `.env` в обоих местах (`POSTGRES_*` и `DATABASE_URL`, пароль в URL — percent-encoded) для запуска API вне Docker. В Compose адрес БД собирается автоматически из `POSTGRES_*`. Образ применяет `POSTGRES_*` только при создании пустого тома: после первого запуска смена значений требует `docker compose down -v`. Остановка — `docker compose stop`, повторный запуск — `docker compose up -d postgres` (данные сохраняются в томе), полный сброс данных — `docker compose down -v`. Контейнер API в Compose обращается к БД по имени сервиса `postgres` в сети `vkr`.

## Конфигурация

Адреса Flask API задаются без суффикса `/api/catalog`:

- `NUXT_API_BASE_URL` — внутренний адрес только для SSR. В Compose задан `http://api:8080`: Docker разрешает имя сервиса `api` внутри общей сети.
- `NUXT_PUBLIC_API_BASE_URL` — адрес для браузера при клиентской навигации; по умолчанию `http://127.0.0.1:8080`, в Compose — `http://localhost:8080`. API разрешает CORS для `http://localhost:3000` и `http://127.0.0.1:3000`.

Если `NUXT_API_BASE_URL` пуст, SSR использует публичный адрес. Поэтому существующая настройка демо Amvera с одной `NUXT_PUBLIC_API_BASE_URL` продолжает работать. Внутренний адрес не передаётся в публичную runtime-конфигурацию. Переменные применяются при запуске, пересборка для смены адреса не нужна. Для dev-сервера шаблон `frontend/.env.example` можно скопировать в `frontend/.env`; production-сервер `.env` не читает, значения передаются через окружение процесса.

`DATABASE_URL` — адрес БД для API и `manage_catalog.py`, формат `postgresql+psycopg://USER:PASSWORD@HOST:5432/vkr`; пароль с особыми символами кодируется percent-encoding. Для локального запуска значение вместе с логином и паролем PostgreSQL лежит в корневом `.env` (шаблон — `.env.example`). Compose читает этот файл автоматически. При запуске API на хосте передайте адрес через окружение терминала. В Amvera это секретная переменная проекта API. Для локальной демонстрации допустима SQLite: `sqlite:////абсолютный/путь/catalog.db`. Ключи платёжных сервисов и другие секреты относятся к целевому backend и не должны попадать в код браузера.

Из Git исключены `.env` и `.env.*` (кроме шаблона `.env.example`), `backend/.venv`, `frontend/node_modules`, `.nuxt` и `.output`.

## Quick Start

Два способа запуска: [запуск в локальном окружении](#запуск-в-локальном-окружении) — Nuxt и Flask с Granian на хосте, PostgreSQL в отдельном контейнере; [полный стенд в Docker](#полный-стенд-в-docker) — все компоненты в контейнерах одной командой.

### Запуск в локальном окружении

Сначала подготовьте `.env` и запустите PostgreSQL по [инструкции выше](#настройки-localhost). Откройте два терминала в корне проекта. Для API нужен Python 3.12 или новее. Выполните блок для своей ОС в первом терминале.

#### Windows (PowerShell)

```powershell
py -3 -m venv backend/.venv
.\backend\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
Remove-Item Env:DATABASE_URL -ErrorAction SilentlyContinue
$env:DATABASE_URL = (docker compose config --environment | Select-String '^DATABASE_URL=').Line -replace '^DATABASE_URL=', ''
Set-Location backend
.\.venv\Scripts\python.exe manage_catalog.py prepare
.\.venv\Scripts\python.exe -m granian --interface wsgi --host 127.0.0.1 --port 8080 --access-log app:app
```

#### Linux или macOS

```sh
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
set -a; . ./.env; set +a
cd backend
.venv/bin/python manage_catalog.py prepare
.venv/bin/python -m granian --interface wsgi --host 127.0.0.1 --port 8080 --access-log app:app
```

При запуске из нового терминала снова загрузите `DATABASE_URL` перед командами из каталога `backend`. Для запуска Nuxt во втором терминале используйте следующие команды (в PowerShell — `npm.cmd` вместо `npm`):

```sh
npm ci --prefix frontend
npm run dev --prefix frontend
```

Открыть `http://127.0.0.1:3000`: `/catalog` рендерится на сервере и показывает 12 товаров из API. Остановить серверы — `Ctrl+C`.

Проверка типов, сборка и тесты frontend выполняются из корня репозитория:

```sh
npm run typecheck --prefix frontend
npm run build --prefix frontend
npm run test:ssr --prefix frontend
```

Тесты API выполняются из каталога `backend` командой `.\.venv\Scripts\python.exe -m unittest discover -s tests -v` в PowerShell или `.venv/bin/python -m unittest discover -s tests -v` в Linux и macOS.

### Полный стенд в Docker

Нужен Docker с Compose v2 и Linux-контейнерами. На Windows запустите Docker Desktop и откройте PowerShell. Сначала остановите запущенные отдельно Granian и Nuxt, чтобы освободить порты `8080` и `3000`. Из корня репозитория:

```sh
docker compose up --build
```

Откройте `http://localhost:3000`, затем каталог. Compose запускает PostgreSQL, ждёт готовности БД, запускает API с миграциями и начальным заполнением, затем frontend после успешной проверки каталога API. Значения по умолчанию позволяют запустить стенд без `.env`; если файл есть, Compose берёт реквизиты БД из `POSTGRES_*`. Существующий том должен соответствовать этим реквизитам.

SSR обращается к `http://api:8080` внутри Docker, браузер — к `http://localhost:8080` через опубликованный порт. Оба адреса уже заданы в Compose, определять LAN IP не нужно. Браузер должен работать на том же компьютере, где запущен Docker. Демо API для этого стенда не используется.

Проверки: `http://localhost:8080/api/catalog` возвращает JSON с товарами; `http://localhost:3000/catalog` содержит товары при прямом открытии и при переходе с главной. Проверки состояния — `http://localhost:8080/healthz` и `http://localhost:3000/healthz`. Все опубликованные порты привязаны к `127.0.0.1`.

Остановка — `Ctrl+C` или `docker compose down`; данные сохраняются в томе. Для запуска только БД при разработке вне контейнеров — `docker compose up -d postgres`. Полный сброс с удалением данных — `docker compose down -v`.

- `frontend/` — приложение Nuxt 4: `app/` (страницы и компоненты), `server/` (серверный маршрут `/healthz`), `shared/`, `tests/` (SSR-тест каталога), `nuxt.config.ts` и lock-файл npm.
- `frontend/Dockerfile` — двухступенчатая сборка на Node.js и runtime-образ `node-server`.
- `backend/` — API на Flask и SQLAlchemy: модели каталога, миграции Alembic, начальные данные, тесты, собственные `Dockerfile` и `amvera.yaml`.
- `amvera.yaml` — конфигурация проекта frontend в Amvera.
- `docker-compose.yml` — локальный стенд PostgreSQL 17, API и frontend в сети `vkr`; отдельно можно запустить только PostgreSQL (контейнер `vkr-postgres`).
- `.env.example` — шаблон локальных переменных: логин, пароль и имя базы PostgreSQL, `DATABASE_URL`; копируется в `.env`.
- `.dockerignore` — ограничение контекста Docker-сборки.

## База данных

Текущий этап включает только `categories` и `products` для отображения каталога. PostgreSQL проекта `vkr-demo` подключён через секретную переменную `DATABASE_URL` в проекте API. Подробные поля, команды и локальная настройка — в [`backend/README.md`](backend/README.md).

### Миграции

Из каталога `backend`: `python manage_catalog.py upgrade`. Alembic создаёт две таблицы каталога и служебную `alembic_version`. При запуске контейнера миграции применяются автоматически до старта Granian.

### Тестовые данные (seed)

`python manage_catalog.py seed` импортирует 7 категорий и 12 товаров из `catalog.json` в пустой каталог. Существующие товары не перезаписываются. JSON используется только для первичного заполнения.

### Тестовая учётная запись

Таблица пользователей и вход по JWT не предусмотрены в первой демо-версии. Каталог и демо-стенд открываются без входа. Сценарий, доступный для повторения сейчас, — просмотр каталога: [`/catalog`](https://tea-shop-frontend-demo-vfirsov.msk1.amvera.tech/catalog) на демо-стенде или `http://127.0.0.1:3000/catalog` после запуска по [Quick Start](#quick-start).

После реализации входа и ролей раздел будет дополнен тестовыми учётными записями покупателя и администратора с реквизитами для повторения сценариев из раздела «Что считать успешным результатом».

### Сброс состояния

Локальная БД: из корня репозитория `docker compose down -v` удаляет контейнер и том с данными, затем `docker compose up -d postgres` создаёт пустую базу. Дождитесь статуса `healthy` в `docker compose ps` и повторите шаг подготовки базы (`manage_catalog.py prepare`) из [инструкции для вашей ОС](#запуск-в-локальном-окружении).

## API

Демо API реализовано в [`backend/`](backend/README.md):

- `GET /healthz` → `200 {"status":"ok"}`.
- `GET /api/catalog` → `200 application/json`: объект с `items` (после начального заполнения — 12 товаров), `total`, `currency: "RUB"`; ответы содержат `Cache-Control: no-store`. Браузерные запросы с домена frontend получают `Access-Control-Allow-Origin` (allowlist в `backend/app.py`). При недоступной БД — `503` с JSON `error`, неизвестный маршрут — `404` с JSON `error`.

Фильтры, пагинация и изменение товаров не реализованы. Полный контракт — в [`backend/README.md`](backend/README.md).

## Тесты

`npm run typecheck --prefix frontend` проверяет типы; `npm run build --prefix frontend` повторяет проверку типов и создаёт production-сборку; `npm run test:ssr --prefix frontend` запускает SSR-интеграционный тест каталога (`node --test`). Backend проверяется unittest-тестами из `backend/tests/` (команда в Quick Start). Нагрузочные тесты пока не настроены.

## Деплой

Код демо размещается в двух проектах Amvera, регион Москва; БД — отдельный проект `vkr-demo`, см. «Демонстрация»:

| | `tea-shop-frontend-demo` | `tea-shop-api-demo` |
|---|---|---|
| Содержимое | структура этого репозитория | каталог `backend/` в корне проекта |
| `amvera.yaml` | корневой (`dockerfile: frontend/Dockerfile`) | `backend/amvera.yaml` |
| Порты | `containerPort` и `servicePort` — `80` | `containerPort` и `servicePort` — `8080` |
| Переменные | `NUXT_PUBLIC_API_BASE_URL` | секретная `DATABASE_URL` (PostgreSQL) |

В обоих `amvera.yaml` `containerPort` и `servicePort` заданы явно и совпадают. По умолчанию Amvera считает оба порта равными `80`; приложение, слушающее не порт 80, без явного `servicePort` снаружи недоступно — домен отвечает `503` при запущенном контейнере. Frontend слушает сам порт `80`: у этого проекта конфигурация `3000`/`servicePort: 3000` не применилась на стороне Amvera — маршрут домена чередовал `503` и таймауты при исправном контейнере. Возврат на `80` (порт, на котором домен работал до перехода на Nuxt) устранил проблему; право binding порта ниже 1024 пользователю `node` даёт `setcap cap_net_bind_service` в `frontend/Dockerfile`.

Порядок обновления каждого проекта:

1. Выполнить локальные проверки и production-сборку.
2. Зафиксировать изменения в Git и доставить их в репозиторий проекта Amvera.
3. При необходимости изменить переменные проекта (`NUXT_PUBLIC_API_BASE_URL` — frontend; `DATABASE_URL` — API; после изменения переменной контейнер перезапускается).
4. Запустить сборку в Amvera, проверить журналы сборки и запуска.
5. Проверить HTTPS, `/healthz`, `/catalog` и ответ `/api/catalog` (12 позиций).

Для отката вернуть в репозиторий проекта содержимое предыдущего рабочего коммита новым коммитом и выполнить пересборку. Переменные окружения не входят в Git и проверяются отдельно; смена `NUXT_PUBLIC_API_BASE_URL` не требует пересборки frontend — достаточно перезапустить контейнер.

### Автоматические обновления

Для автоматических обновлений выбрана ветка `main`. Нативный webhook GitHub → Amvera пока **не настроен**: доступный MCP не содержит метода его настройки, а управление браузером в текущей сессии недоступно. Подключение вручную по [документации Amvera](https://docs.amvera.ru/applications/git/webhooks.html): в проекте frontend включить ручную настройку подключения GitHub (репозиторий `vfirsov/vfirsov-vr22-vkr`, ветка `main`, событие Push), затем добавить webhook с тем же секретом в настройках GitHub. Для проекта API содержимое каталога `backend/` доставляется в репозиторий проекта напрямую; webhook для него не используется.
