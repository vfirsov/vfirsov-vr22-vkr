# План приведения репозитория в соответствие требованиям ВКР

**Источник требований:** `docs/2.09 ВР.pdf` — «GitHub-репозиторий ВКР по веб-разработке» (21 слайд).
**Предмет работы:** «Разработка информационной веб-системы для управления продажами и учета
ассортимента в чайном магазине» (`docs/Фирсов В.Д. ВР-22з.docx`, `docs/Отчет Фирсов В Д 3Б-ВР-22.docx`).

Главный тезис презентации: *репозиторий — часть результата ВКР*. Демонстрация на ноутбуке
заканчивается вместе с защитой, а репозиторий должен сохранять код, конфигурацию и способ
проверки так, чтобы **новый пользователь получил результат без устных пояснений**.

---

## 1. Аудит текущего состояния

```
.gitignore                              # базовый, только ОС/редакторы/Office
README.md                               # одна строка: "# vfirsov-vr22-vkr"
docs/2.09 ВР.pdf                        # презентация с требованиями
docs/Отчет Фирсов В Д 3Б-ВР-22.docx     # отчёт
docs/Фирсов В.Д. ВР-22з.docx            # текст ВКР
```

Ключевой вывод аудита: **в репозитории нет ни строки кода системы**. Это отличает ситуацию от
«учебного антипримера» из презентации (где есть `client_final`, `server2`, `database.sql` без
объяснений): здесь нет ни блокеров в виде утёкших секретов, ни мусорных каталогов — но нет и
проверяемого пути. По восьми критериям презентации репозиторий на данный момент не выполняет
ни одного.

Это даёт преимущество: структуру можно построить сразу правильно, не разбирая легаси.

### Соответствие восьми критериям — исходная точка

| № | Критерий | Статус | Разрыв |
|---|----------|--------|--------|
| 1 | Назначение и результат | ✗ | README не называет задачу, пользователей, вклад автора, критерий успеха |
| 2 | Стек и требования | ✗ | версии Python/Node/PostgreSQL, пакетный менеджер, lock-файлы не зафиксированы |
| 3 | Копируемый Quick Start | ✗ | нет команд запуска, нет `compose.yml` |
| 4 | Конфигурация и секреты | ◐ | `.env` не исключён в `.gitignore`, `.env.example` отсутствует (секретов в Git нет — это плюс) |
| 5 | Структура компонентов | ✗ | нет `frontend/`, `backend/`, `infra/`, `tests/` |

| 8 | Деплой, безопасность, лицензия | ✗ | нет LICENSE, `.dockerignore`, раздела ограничений |

## 2. Целевая структура репозитория

Структура из слайда «Структура объясняет состав системы», наполненная стеком из раздела 2.1 ВКР
(Flask + SQLAlchemy + PostgreSQL + Vue.js + Bootstrap, Gunicorn/Nginx, Docker, pytest):

```
README.md                      # точка входа: цель, состав, запуск, проверка
LICENSE                        # MIT
CONTRIBUTING.md                # как запустить проверки локально (опционально)
.env.example                   # полный перечень переменных с безопасными значениями
.gitignore                     # + .env, venv, node_modules, __pycache__, dist
.dockerignore                  # исключает .git, node_modules, docs, tests из образов
compose.yml                    # db + backend + frontend одной командой
Makefile                       # up / down / migrate / seed / reset / test / lint

backend/                       # API и бизнес-логика (Flask + SQLAlchemy)
  app/
    __init__.py                # application factory, регистрация blueprint'ов
    config.py                  # чтение конфигурации только из окружения
    models/                    # clients, categories, products, orders, order_items,
                               # payments, deliveries, admins, history
    api/                       # auth, catalog, cart, orders, admin, reports
    services/                  # расчёт суммы заказа, проверка остатков, статусы
    schemas/                   # валидация входных данных и сериализация
  migrations/                  # Alembic: версионированная схема
  seeds/                       # безопасные тестовые данные (справочники + демо-товары)
  tests/                       # unit + API-тесты (pytest)
  pyproject.toml               # зависимости и версия Python
  requirements.lock            # (или uv.lock / poetry.lock) — воспроизводимая сборка
  Dockerfile

frontend/                      # клиентское приложение (Vue.js + Bootstrap)
  src/
    views/                     # каталог, карточка товара, корзина, заказ, админка
    components/
    api/                       # обёртка над fetch, базовый URL из переменной окружения
  package.json
  package-lock.json
  Dockerfile

infra/
  nginx/nginx.conf             # reverse proxy, раздача статики
  gunicorn.conf.py
  compose.prod.yml             # production-конфигурация, отделённая от локальной
  backup/pg_dump.sh            # резервное копирование (нефункциональное требование ВКР)

docs/
  2.09 ВР.pdf                  # требования (как есть)
  Фирсов В.Д. ВР-22з.docx      # текст ВКР (как есть)
  Отчет Фирсов В Д 3Б-ВР-22.docx
  PLAN.md                      # этот файл
  architecture.md              # схема компонентов и потоков данных
  data-model.md                # ER-диаграмма и описание таблиц
  openapi.yaml                 # контракт REST API
  demo.md                      # URL стенда / статус стенда, тестовая учётная запись
  adr/                         # architecture decision records
    0001-stack-flask-vue-postgres.md
    0002-alembic-instead-of-sql-dump.md
    0003-jwt-auth-and-roles.md

tests/
  e2e/                         # сквозной сценарий: регистрация → корзина → заказ → статус
```

Два отличия от буквального текста ВКР, которые нужно зафиксировать осознанно:

1. **Миграции вместо SQL-скриптов.** В разделе 2.5 ВКР схема создаётся «ранее подготовленными
   SQL-скриптами», а презентация прямо называет `database.sql` вместо миграций антипримером.
   Решение: Alembic как единственный источник схемы, SQL-дампы не публикуются. Обосновать в
   `docs/adr/0002-alembic-instead-of-sql-dump.md`.
2. **Каталог `adr/`.** Коммит `bab80f9` называется «add adr folder», но каталог так и не появился.
   План закрывает это расхождение.

## 3. Этапы работ

Порядок взят со слайда «Исправление начинается с блокеров» и адаптирован под то, что секретов в
Git нет, поэтому шаг отзыва ключей сводится к превентивной настройке.

### Этап 0. Блокеры и границы доверия (приоритет — первый)

- [ ] Добавить в `.gitignore`: `.env`, `.env.*` (кроме `.env.example`), `venv/`, `.venv/`,
      `node_modules/`, `__pycache__/`, `*.pyc`, `dist/`, `.pytest_cache/`, `uploads/`, `*.sql`,
      `*.dump`.
- [ ] Создать `.dockerignore` (`.git`, `docs`, `tests`, `node_modules`, `__pycache__`, `.env*`).
- [ ] Создать `.env.example` с полным перечнем переменных и **безопасными** значениями, достаточными
      для учебного запуска (см. § 4).
- [ ] Добавить `LICENSE` (MIT) — критерий 8.
- [ ] Проверить, что в истории Git нет секретов: `git log -p | grep -iE "password|secret|token|api[_-]key"`.
      Если найдутся — отозвать ключ у провайдера и переписать историю, а не просто удалить файл.
- [ ] Убедиться, что seed не содержит реальных персональных данных покупателей.

**Критерий приёмки:** `git ls-files` не содержит `.env`, дампов БД и артефактов сборки; `LICENSE`
и `.env.example` на месте.

### Этап 1. README как точка входа

Переписать `README.md` по минимальной структуре из презентации (§ 5 этого плана). Цель —
четыре вопроса закрываются за первые 60 секунд: **цель, состав, запуск, проверка**.

- [ ] Назначение: какую задачу решает система (учёт ассортимента и управление продажами в чайном
      магазине), кто основные пользователи (покупатель, администратор), что именно разработано
      автором ВКР, что считать успешным результатом.
- [ ] Состав системы: frontend (Vue.js), backend (Flask REST API), PostgreSQL, внешние сервисы
      (платёжный шлюз, служба доставки) — с пометкой, какие из них заглушки.
- [ ] Ссылка на стенд или честная отметка его состояния («стенд не публикуется, запуск локальный»).
- [ ] Ссылки на `docs/architecture.md`, `docs/data-model.md`, `docs/openapi.yaml`.

**Критерий приёмки:** человек, не видевший защиту, по README называет цель системы, её состав и
команду запуска.

### Этап 2. Стек, требования и Quick Start

- [ ] Зафиксировать версии: Python (например 3.12), Node.js (например 20 LTS), PostgreSQL
      (например 16), Docker Compose v2. Указать выбранный пакетный менеджер и закоммитить
      lock-файлы (`requirements.lock`/`uv.lock` и `package-lock.json`) — критерий 2.
- [ ] Написать `compose.yml`: сервисы `db`, `backend`, `frontend` с healthcheck у `db`, чтобы
      миграции не стартовали раньше базы.
- [ ] `Makefile` с целями `up`, `down`, `migrate`, `seed`, `reset`, `test`, `lint`.
- [ ] Quick Start в README — строго копируемая последовательность без догадок:
      `git clone` → `cd` → `cp .env.example .env` → `docker compose up -d` → `make migrate` →
      `make seed` → URL → `docker compose down` (и `make reset` для сброса состояния).
- [ ] Указать поддерживаемые ОС и известные ограничения (например, занятые порты 5173/8000/5432).

**Критерий приёмки:** на чистой машине без Python и Node, только с Docker, последовательность из
README поднимает систему и отдаёт рабочий URL.

### Этап 3. Схема БД: миграции и seed

Модель данных берётся из разделов 2.3–2.4 ВКР.

- [ ] Описать модели SQLAlchemy для девяти таблиц: `clients`, `categories` (иерархия через
      `parent_id`, уникальность `name + parent_id`), `products` (`tea_type`, `origin_country`,
      `packaging_weight`, `brewing_recommendation`, `stock_quantity`, `is_active`, `image_url`),
      `orders`, `order_items` (с `price_at_order`, не обновляемым при смене цены), `payments`,
      `deliveries`, `admins`, `history` (аудит действий).
- [ ] Индексы по ВКР: составной `products(category_id, is_active)`; `orders(status, created_at)`;
      `products(tea_type)`, `products(origin_country)`; уникальный `clients(email)`.
- [ ] Ссылочная целостность: `ON DELETE RESTRICT` / `SET NULL` по смыслу; удаление клиента не
      удаляет его заказы.
- [ ] Первая миграция Alembic, воспроизводящая схему целиком; `make migrate` применяет её.
- [ ] Seed: справочники (типы чая, страны, категории, способы доставки) + 15–20 демо-товаров с
      описаниями и рекомендациями по завариванию + **тестовые учётные записи покупателя и
      администратора**, вынесенные в README.
- [ ] `make reset` — команда сброса состояния (drop + migrate + seed).
- [ ] Решить открытый вопрос: таблицы корзины (`carts`/`cart_items`) и отзывов (`reviews`) есть в
      функциональных требованиях раздела 1.2 ВКР, но отсутствуют в физической модели раздела 2.4.
      Либо добавить их в схему, либо честно отнести к ограничениям в README.

**Критерий приёмки:** `make reset` на пустом томе даёт идентичное состояние БД; реальные дампы и
персональные данные в репозиторий не попадают.

### Этап 4. API-контракт, тесты и CI

- [ ] Реализовать маршруты (раздел 2.5 ВКР): регистрация, вход (JWT), восстановление пароля,
      каталог с фильтрами (тип, регион, цена, наличие, вкусовые свойства), карточка товара,
      корзина, оформление заказа, статус заказа; админские CRUD товаров, смена статуса заказа,
      отчёты по продажам и остаткам.
- [ ] Хеширование паролей, разграничение прав покупатель/администратор, валидация загружаемых
      изображений по типу и размеру.
- [ ] Зафиксировать контракт в `docs/openapi.yaml` (критерий 7) и сослаться на него из README.
- [ ] Тесты (pytest): модели и расчёт суммы заказа; API каждого маршрута; **сквозной сценарий из
      таблицы 4 ВКР** — регистрация → добавление в корзину → оформление заказа → смена статуса
      администратором → клиент видит новый статус.
- [ ] Указать команду тестов в README: `make test`.
- [ ] GitHub Actions (`.github/workflows/ci.yml`): линт (ruff/black, eslint), `pytest` с сервисом
      PostgreSQL, сборка frontend, smoke-проверка `docker compose up` + миграции + healthcheck.

**Критерий приёмки:** CI зелёный на каждом push; основной пользовательский сценарий подтверждён
автоматическим тестом, а проверка соответствует заявленному в README результату.

### Этап 5. Деплой, безопасность, ограничения

- [ ] `infra/compose.prod.yml` + `infra/nginx/nginx.conf` + `infra/gunicorn.conf.py` — связка
      Gunicorn/Nginx на Ubuntu Server из раздела 2.1 ВКР; локальная и production-конфигурации
      разделены (критерий 8).
- [ ] `infra/backup/pg_dump.sh` и описание расписания — нефункциональное требование о ежесуточном
      резервном копировании.
- [ ] Раздел README «Безопасность»: HTTPS, хеширование паролей, параметризованные запросы через
      SQLAlchemy как защита от SQL-инъекций, отсутствие секретов в репозитории.
- [ ] Раздел README «Известные ограничения» — честно: по результатам раздела 2.7 ВКР система
      устойчива до ~100 RPS, выше растут задержки из-за синхронного Flask и отсутствия кэширования;
      платёжный шлюз и служба доставки подключены в тестовом режиме/заглушками; нет Redis-кэша.
- [ ] Способ сообщить об ошибке: GitHub Issues + шаблон `.github/ISSUE_TEMPLATE/bug_report.md`.
- [ ] ADR по трём решениям: стек, Alembic вместо дампа, JWT и модель ролей.

**Критерий приёмки:** ограничения названы до того, как их найдёт комиссия; production-конфигурация
не смешана с локальной.

## 4. Перечень переменных для `.env.example`

Безопасные значения, достаточные для учебного запуска; production-значения не публикуются.

| Переменная | Назначение | Значение-пример |
|------------|------------|-----------------|
| `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` | параметры локальной БД | `tea_shop` / `tea` / `tea_local_dev` |
| `DATABASE_URL` | строка подключения SQLAlchemy | `postgresql+psycopg://tea:tea_local_dev@db:5432/tea_shop` |
| `FLASK_ENV` / `LOG_LEVEL` | режим и логирование | `development` / `INFO` |
| `SECRET_KEY` | подпись сессий Flask | `change-me-in-production` |
| `JWT_SECRET_KEY` / `JWT_ACCESS_TOKEN_EXPIRES` | аутентификация | `change-me-in-production` / `3600` |
| `CORS_ORIGINS` | допустимые источники для SPA | `http://localhost:5173` |
| `UPLOAD_DIR` / `MAX_UPLOAD_SIZE_MB` | изображения товаров | `./uploads` / `5` |
| `VITE_API_BASE_URL` | базовый URL API для frontend | `http://localhost:8000/api` |
| `PAYMENT_PROVIDER` / `PAYMENT_SHOP_ID` / `PAYMENT_SECRET_KEY` | платёжный шлюз (YooKassa, тест) | `stub` / пусто / пусто |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASSWORD` | уведомления о статусе заказа | `localhost` / `1025` / пусто / пусто |
| `GUNICORN_WORKERS` | параметр production-запуска | `4` |

Правила: `.env` исключён из Git; production-пароли и токены не публикуются; при компрометации
ключ отзывается у провайдера, а не просто удаляется из файла.

## 8. Риски и вопросы к уточнению

| Вопрос | Почему важен | Предлагаемое решение по умолчанию |
|--------|--------------|-----------------------------------|
| Есть ли код прототипа вне репозитория? | Если прототип из раздела 2.5 ВКР существует локально, этапы 3–4 — это перенос и приведение к структуре, а не разработка с нуля | исходить из разработки с нуля, при появлении кода — импортировать в `backend/`/`frontend/` |
| Будет ли публичный стенд? | Критерий 1 требует либо URL, либо честной отметки состояния | отметить «стенд не публикуется, запуск локальный через Docker» |
| Корзина и отзывы в схеме БД | расхождение разделов 1.2 и 2.4 ВКР | добавить `carts`/`cart_items`/`reviews` в схему; иначе — в раздел ограничений |
| Платёжный шлюз: тестовый режим или заглушка? | нельзя публиковать реальные ключи YooKassa | заглушка `PAYMENT_PROVIDER=stub`, тестовые ключи только через локальный `.env` |
| Лицензия | критерий 8 | MIT, если у вуза нет иных требований |

## 9. Порядок выполнения

Этапы 0 и 1 дают максимальный эффект при минимальных затратах и выполняются первыми: они
закрывают границы доверия и четыре вопроса первых 60 секунд. Этап 2 делает репозиторий
запускаемым, этапы 3–4 — проверяемым, этап 5 — пригодным к публикации. Каждый этап завершается
отдельным коммитом со своим критерием приёмки, чтобы прогресс был виден в истории.
